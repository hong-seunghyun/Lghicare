# 상품 데이터 운영 최적화 제안

추천 방향은 **시트·Drive는 편집용으로 유지하고, 고객 화면은 검증 후 게시한 데이터·이미지를 조회**하는 구조입니다. 현재 익숙한 관리 방식은 유지하면서 조회 속도와 가격 변경 이력을 개선할 수 있습니다. 이 문서는 제안이며 새 클라우드 자원 생성, 유료 서비스 가입, 데이터 이전 및 운영 배포는 진행하지 않았습니다.

## 현재 코드에서 확인한 병목

- `src/pages/api/products.ts`: 3개 모델만 요청해도 중분류 캐시를 만들 때 모든 하위 모델 폴더의 이미지를 검색합니다. 클라이언트에는 모든 가격 옵션을 보냅니다.
- `src/lib/sheet.ts`: 기본 원본 시트 캐시는 30일입니다. 목록 캐시·CDN·브라우저 캐시도 별도로 있어서, 캐시 삭제 방식에 따라 갱신 시점이 달라집니다.
- `src/pages/api/image-proxy.ts`: 서버가 Drive 원본 파일을 스트리밍합니다. 브라우저에서 작게 표시해도 원본 다운로드 경로를 거칩니다.
- 서버 메모리 캐시는 프로세스·인스턴스별로 분리됩니다. 여러 인스턴스로 늘리면 같은 Google API 조회가 반복될 수 있습니다.

## 이번에 적용한 범위

- 리뉴얼 테마상품 전용 `/api/renewal/theme-products`를 추가했습니다. 모델 3개만 조회하고 카드용 최저가·선택 조건만 전송합니다. 전체 옵션은 제품 선택 후 기존 API에서 조회합니다.
- 중분류의 폴더 이름 목록은 재사용하고, 지정 모델 폴더의 이미지만 조회합니다. 같은 요청과 폴더 조회는 진행 중인 Promise를 공유합니다.
- 기존 시트 조회 정책은 유지하면서 새 테마 경로에만 5분 원본 캐시와 오래된 가격 반환 금지를 적용했습니다. 실패하면 재시도를 표시합니다. 브라우저 요약 캐시는 1분이며 CDN 캐시도 있어, 즉시 게시를 보장하는 버전 관리 구조는 아닙니다.
- 테마 탭 hover/focus 시 해당 탭을 미리 읽고, 이미지에는 Next.js의 화면 크기별 최적화 출력을 사용합니다.
- 같은 냉장고 3개 모델의 응답 본문이 141,265바이트에서 1,735바이트로 약 98.8% 감소했습니다. 이는 **응답 데이터 크기** 비교이며 첫 방문 전체 로딩 시간이 98.8% 단축되었다는 의미는 아닙니다.

## 권장 구조

관리자는 시트의 가격·옵션과 Drive 원본 사진을 편집합니다. 관리자 화면의 ‘검증 후 게시’ 작업이 모델명, 요금, 허용 옵션, 누락 이미지 등을 확인한 뒤 공개용 카탈로그와 모델별 옵션 파일을 생성합니다. 사이트는 이 게시본을 읽고, 기존 로그인·매니저 권한은 유지합니다.

| 저장 위치 | 역할 |
| --- | --- |
| Google Sheets | 관리자가 수정하는 상품·옵션 원본 |
| Google Drive | 원본 사진 보관·편집 |
| Firestore | 게시 버전, 활성 카탈로그·테마 설정, 변경 이력 |
| Cloud Storage | 모델별 옵션 JSON, 320/640/960px WebP 등 공개용 사진 |
| 기존 상품 API | 현재 게시 버전의 카탈로그·옵션을 읽어 기존 화면과 연결 |

모든 모델의 옵션을 하나의 Firestore 문서에 넣지 않고, 모델별로 나누거나 Storage의 모델별 JSON을 사용합니다. 견적에는 `catalogVersion`과 저장 당시 가격·조건을 함께 기록합니다. 가격을 갱신할 때는 차이를 확인하고 적용하며, 새 데이터 검증에 실패하면 기존 게시본을 유지합니다.

## 적용 순서

1. **단기:** 이번 경량 테마 조회를 기준으로 상품 목록에도 요약 API를 적용하고, 최저가·계약·카드 요금 기준을 일관되게 유지합니다. 이미지 크기와 실제 첫 방문 로딩 시간을 따로 측정합니다.
2. **우선 권장:** ‘검증 후 게시’와 버전·롤백을 도입합니다. 이미지 변환·업로드를 게시 작업에서 처리해 사용자 접속 시 Drive 탐색을 제거합니다. 파일명은 콘텐츠 해시 또는 게시 버전을 포함해 변경 시 새 URL을 사용합니다.
3. **필요할 때:** 예약 동기화 또는 Drive 변경 내역을 활용한 증분 동기화를 추가합니다. 실패한 항목과 마지막 성공 시각을 관리자에게 보여주고, 게시 도중 일부 가격만 섞여 노출되지 않게 활성 버전을 마지막에 전환합니다.

새 비용과 작업 기간은 상품·옵션 수, 원본 이미지 크기, 월 트래픽을 확인한 뒤 산정하는 편이 좋습니다. 현재 단계에서는 SQL 전면 이전보다 기존 Firebase와 편집 도구를 활용한 게시 구조가 변경 범위를 줄입니다.

## 공식 문서

- [Cloud Storage 캐싱](https://docs.cloud.google.com/storage/docs/caching): 공개 객체의 캐싱 조건과 Cache-Control. 공개 이미지·카탈로그만 대상으로 하고 인증 토큰·고객 견적은 공개 캐시에 넣지 않습니다.
- [객체 메타데이터](https://docs.cloud.google.com/storage/docs/metadata): 콘텐츠 유형과 Cache-Control 설정.
- [Drive 변경 내역 조회](https://developers.google.com/workspace/drive/api/guides/manage-changes): change token으로 바뀐 파일을 이어서 조회하는 방식.
- [Sheets API 사용량 제한](https://developers.google.com/workspace/sheets/api/limits): 요청 한도와 백오프. 동기화 시 필요한 범위만 묶어 읽고 재시도를 제어합니다.
